INTEGRATEDDESIGN CHECKLIST

This page translates the documentation into a media plan. For each page, it identifies whether the reader needs a diagram, a true UI screenshot, or an output example. The goal is to make the site easier for new people without filling every page with redundant images.

ON THIS PAGE

How to use this checklist

  • Diagram means a conceptual drawing is enough; it explains structure better than a screenshot.
  • UI screenshot means the reader needs to see a real panel, overlay, or control layout.
  • Output example means the page benefits from one or more still frames produced by HUFF.
  • Priority tells you what to capture first if time is limited.
Best first capture set. If you only gather a few images now, start with: the full control window, the output window, the VERIFY overlay, the INTEROP overlay, the routing/recipe controls, the export overlay, and four strong output stills showing different visual looks.

Immediate capture priorities

  1. Capture one clean full-window screenshot of the control surface.
  2. Capture one screenshot of the output window showing a strong visual state.
  3. Capture VERIFY and INTEROP overlays.
  4. Capture the routing/recipe controls and the export controls.
  5. Render 4–8 good output stills for the public-facing gallery.
  6. Only after that, capture secondary screens such as MIDI, OSC, presets, and queue.

What can stay diagram-only

Architecture, temporal memory, routing concepts, and output paths are best communicated by diagrams. Screenshots do not explain these relationships well enough on their own.

What absolutely needs real screenshots

Interface Tour, MIDI, OSC, Verification, Interop, and export controls should show the actual UI. Those pages describe concrete operator workflows, so diagrams alone would feel too abstract.
